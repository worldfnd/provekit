ProveKit is a Noir-to-WHIR proof system and runtime. You write a circuit in [Noir](https://noir-lang.org/); ProveKit compiles it to R1CS, generates [WHIR](https://eprint.iacr.org/2024/1586.pdf) proofs from your inputs, and verifies those proofs from Rust, WebAssembly, mobile FFI, an HTTP service, or via a Groth16 outer proof for on-chain settlement.

If you've never used a ZK proof system before, this page is the right place to start. You don't need to know cryptography to use ProveKit. You do need to understand what kind of guarantee a proof gives you, and where ProveKit fits in your stack.

## The problem ProveKit solves

A zero-knowledge proof lets one party (the **prover**) convince another (the **verifier**) that a statement is true, *without revealing the data that makes the statement true*.

A few statements ProveKit can help you prove:

- "I am over 18", without revealing a date of birth.
- "I own a passport issued by country X", without revealing the passport.
- "This vote came from a registered voter", without revealing which voter.
- "This off-chain computation produced this result", without re-running it on-chain.

The workflow is the same shape every time:

1. **Author a circuit** in Noir. A small program defining what counts as "true."
2. **Prepare** prover and verifier keys from the compiled circuit.
3. **Prove** a specific instance using your real (private) inputs and the prover key.
4. **Verify** the proof anywhere using the verifier key and the public inputs.

ProveKit owns steps 2–4 and the runtime that runs them on every platform you ship to. You bring the Noir circuit; ProveKit handles the rest.

## What's in the box

ProveKit is a workspace of focused Rust crates plus tooling. Each piece has one job:

| Crate / tool | Job |
| :--- | :--- |
| [`provekit-r1cs-compiler`](https://github.com/worldfnd/provekit/tree/main/provekit/r1cs-compiler) | Lower Noir's ACIR (and optionally Mavros) into R1CS, with specialized handling for Poseidon2, SHA-256 compression, range checks, multi-scalar multiplication, and Spartan-shaped uints. |
| [`provekit-prover`](https://github.com/worldfnd/provekit/tree/main/provekit/prover) | Solve the witness in layers, compress the R1CS for low-memory proving, commit via Merkle hashing, and produce the WHIR proof via Spartan-style sumcheck. |
| [`provekit-verifier`](https://github.com/worldfnd/provekit/tree/main/provekit/verifier) | Replay the Fiat-Shamir transcript, run sumcheck verification, and bind the public inputs. |
| [`provekit-cli`](https://github.com/worldfnd/provekit/tree/main/tooling/cli) | The command-line entry point — `prepare`, `prove`, `verify`, plus inspection and recursive-verifier export. |
| [`provekit-wasm`](https://github.com/worldfnd/provekit/tree/main/tooling/provekit-wasm) | Browser and Node.js bindings using `wasm-bindgen-rayon` for in-browser parallel proving when `SharedArrayBuffer` is available. |
| [`provekit-ffi`](https://github.com/worldfnd/provekit/tree/main/tooling/provekit-ffi) | C ABI for Swift, Kotlin, Python, and any host that can call a shared library. Includes an mmap-backed allocator for mobile circuits that exceed RAM. |
| [`verifier-server`](https://github.com/worldfnd/provekit/tree/main/tooling/verifier-server) | An Axum HTTP service that downloads artifacts and orchestrates verification with configurable concurrency and timeouts. |
| [`recursive-verifier/`](https://github.com/worldfnd/provekit/tree/main/recursive-verifier) | A Go/gnark module that wraps a ProveKit proof in Groth16 so it can be verified by an EVM contract. |
| [`skyscraper`](https://github.com/worldfnd/provekit/tree/main/skyscraper) | A custom BN254 hash engine with SIMD-accelerated field arithmetic on `aarch64`. The default Merkle commitment and Fiat-Shamir transcript hash. |

## What makes ProveKit specifically different

If you've seen other ZK proof systems before, the differentiators are:

- **WHIR backend.** Modern polynomial commitment scheme with no trusted setup for the base proof. Spartan-style sumcheck for fast verification.
- **BN254 field.** Lines up with EVM contracts when settlement on-chain is needed via the Groth16 wrapper.
- **Memory-conscious proving.** Witness builders execute in layers; the R1CS is compressed to a postcard blob during proving to keep peak memory low. Mobile FFI ships with a file-backed mmap allocator so circuits exceeding device RAM still prove.
- **Multi-host runtime from one codebase.** The same `.pkp` and `.pkv` artifacts drive native Rust, WASM (browser and Node), iOS, Android, an HTTP service, and the recursive verifier. Most ZK toolkits leave this integration story to you.
- **Hash choice as a first-class artifact property.** `--hash` selects Skyscraper, SHA-256, Keccak, Blake3, or Poseidon2 for Merkle commitments and the Fiat-Shamir transcript. The chosen hash is part of the artifact's identity.

## When to use ProveKit

| You're doing this... | ProveKit fits when... |
| :--- | :--- |
| Building a ZK app from a Noir circuit | You want one proving pipeline that works on server, browser, and mobile. |
| Proving things about identity / credentials | Your verifier may run in many places (phone, server, chain). |
| Pushing computation off-chain | You want to verify cheaply on-chain via a Groth16 wrapper. |
| Privacy-preserving data attestation | You need to ship the verifier to untrusted devices. |
| Prototyping a ZK feature | The CLI lets you iterate on circuits without writing host integration code. |

## When *not* to use ProveKit

- **You haven't decided on Noir.** ProveKit is Noir-first. If you're committed to Circom, Halo2, or another DSL, look elsewhere.
- **You need a battle-tested production system today.** ProveKit is under active development. `main` may change formats; pin `v1` and read [Project status](/reference/project-status/) before shipping.
- **You need direct on-chain verification (no wrapper).** Today, on-chain settlement requires the Groth16 wrapper via the [recursive verifier](/integrations/overview/#recursive-verifier--gnark).

## You don't need to know

You can use ProveKit without ever touching:

- **Field arithmetic.** Noir hides the BN254 field. Public inputs are typed values, not raw field elements.
- **WHIR internals.** ProveKit picks the polynomial commitment, sumcheck protocol, and Fiat-Shamir transcript. You pick the hash configuration via `--hash`.
- **R1CS.** Noir compiles to ACIR; ProveKit lowers ACIR to R1CS. You never write a constraint by hand unless you want to (see the Mavros backend).
- **Recursive verifier internals.** If you need on-chain settlement, ProveKit exports the inputs and the Go/gnark wrapper handles the rest.

## You do need to know

- **What's public and what's private.** Public inputs are part of the proof contract — they're bound into verification. Your application decides what those inputs mean.
- **That artifacts are versioned.** A `.pkp` and `.pkv` from one preparation run are not compatible with proofs from another run. ProveKit treats them as deployment artifacts. See [Artifact lifecycle](/concepts/artifact-lifecycle/).
- **That verification proves the proof, not your policy.** A successful verification says the proof is valid against the verifier key and public inputs. Your application still owns the decision about whether those inputs *authorize* the requested action. See [Security and trust model](/concepts/security-model/).

## A worked picture

The checked-in `noir-examples/basic` circuit proves you know two field elements that hash (via Poseidon2) to a known commitment:

```rust
use dep::poseidon2;

fn main(plains: [Field; 2], result: pub Field) {
    let hash = poseidon2::bn254::hash_2(plains);
    assert(hash == result);
}
```

`plains` is private — only the prover sees it. `result` is public — it goes into the proof. A successful verification means *the prover knows two field elements that hash to `result`*, and the verifier learns the prover does, without learning `plains`.

That tiny circuit is the same shape as much bigger ones: identity attestation, set membership, off-chain computation, range proofs. Once you can build, prove, and verify this one, every other circuit follows the same workflow.
